# План аппаратной приёмки 0.20.3

**Статус:** CI и mock-UCI не заменяют испытание на реальном OpenWrt. Этот план рассчитан на отдельный испытательный маршрутизатор с локальным Ethernet-доступом и запасным каналом управления. Не проводить рискованные тесты удалённо без консоли/резерва.

## Матрица

| Испытание | OpenWrt 24.10 (opkg) | OpenWrt 25.12 (apk) |
| --- | --- | --- |
| Forkop 2.0 | требуется | требуется |
| Podkop Experimental 0.8.21 | требуется | требуется |
| BearGuard 0.20.3-r1 поверх 0.20.2-r3 | требуется | требуется |
| Чистая установка и повторная установка | требуется | требуется |

## До обновления

1. Обеспечить локальный доступ (Ethernet/serial) и восстановительный маршрут. Записать IP роутера, версию прошивки, движок, UCI schema, версию бота, способ установки и хеш пакета.
2. Сделать внешнюю копию всех `/etc/config/podkop`, `/etc/config/forkop`, `/etc/config/podkop_bot`, `/etc/config/podkop_bearhole`, если они существуют. Защитить файл с токеном Telegram и паролями; **не загружать UCI-конфигурации в публичные issues**.
3. Убедиться в исходно исправном доступе в сеть, маршрутизации и Telegram. Зафиксировать значения DNS/WAN и порядок секций.

## Проверки

1. Установить тестовый артефакт BearGuard из успешной CI данного PR для соответствующего пакетного менеджера. Проверить, что пакет `0.20.3-r1`, встроенный `BOT_VERSION=0.20.3-dev4`; `sha256sum -c /usr/lib/podkop_bot/vendor.sha256` из каталога `/usr/lib/podkop_bot` возвращает OK.
2. Проверить сохранность токена, подписок, настроек Bearhole, WARP и Tailscale; нельзя допускать самопроизвольного сброса UCI при обновлении.
3. В Telegram: открыть и сохранить уже существующий список серверов/доменов; создать и удалить запись; убедиться, что unrelated UCI-секции не меняются.
4. Для Podkop Experimental: добавить DNS `udp 1.1.1.1` и `doh dns.google/dns-query`, переставить порядок, заменить на `provider`, удалить не последнюю строку. Проверить отрисовку того же списка в штатном LuCI и фактический DNS-resolve после каждого применения.
5. Для Forkop 2: DNS main/bootstrap списки, fallback `parallel/sequential`, detour только на существующую секцию, стратегия IPv4/IPv6, WAN output, BadWAN и BitTorrent direct; убедиться, что изменения читаются штатным LuCI Forkop 2.
6. Для обоих: IPv4/IPv6 исключения, сохранение списка LAN-устройств, запрет удаления последнего обязательного DNS и интерфейса.
7. Проверить отключение/включение секции, выбор сервера, обновление подписки, работу Mixed Proxy и основного Telegram-транспорта после `reload`.
8. Негативный тест **только на резервном стенде**: заставить движок отклонить изменение/имитировать сбой reload; проверить, что бот возвращает состояние ошибки, конфигурация восстановлена и соединение снова работает. Если повторное восстановление не удаётся, бот обязан сообщить аварийное состояние, а не успех.
9. Повторить тесты после перезагрузки роутера. Проверить `logread` и отсутствие повторных служб/процессов.
10. Обновить бота из установленного BearGuard. Проверить защиту от случайного понижения `dev4` до более старого стабильного бота.

## Признаки прохождения

- Нет регрессии доступа по Ethernet, LAN, DNS, Telegram; двигатель принимает конфигурацию после изменения, перехода на новый движок и ребута.
- Полная запись совпадает со штатной UCI-схемой; пароли, токены и существующие пользовательские строки сохранены.
- В случае отказа reload понятная диагностика + подтверждённое восстановление, иначе аварийный результат и инструкция ручного восстановления.
- Нет одновременных конфликтующих записей из BearGuard/LuCI/Telegram; не остаётся некорректных временных `uci` delta.
- Результаты испытаний записаны **для всех четырёх комбинаций** движка и пакетного менеджера; каждый негативный тест связан с воспроизводимым логом без персональных данных.

**Текущий статус:** до проведения испытаний выше нельзя сливать PR #18 и #27 в `main` и публиковать стабильный `v0.20.3`.
